01 Start here

What LecGap is, in one paragraph

LecGap is a lecture-comprehension gap detector. You give it a recorded lecture. It listens to the recording, works out which concepts were taught and which concepts must be understood before others, then quizzes students. When a student gets something wrong, LecGap walks backwards through the concept graph and produces a study plan ordered from the earliest prerequisite to the thing that was missed. Each step links to the exact video clip where that concept was taught.

The student story

  1. Upload a lecture recording.
  2. Wait for transcription and concept extraction.
  3. Open the concept map and see what depends on what.
  4. Take a short diagnostic quiz.
  5. Receive a remediation plan in the correct learning order.
  6. Watch the matching lecture clips.

The instructor story

  1. See every prerequisite edge the system found, with confidence and spoken evidence.
  2. See where the class is getting confused.
  3. Compare the order concepts were taught with the order the graph says they should be learned.
  4. See how much of a lecture's spoken time is covered by extracted concepts.
  5. Rebuild the graph when new lectures arrive.
Current frontend, not the old one

The active UI is frontend-react/, built with React, Vite, TypeScript, Material UI, React Query, Zustand, and React Flow. The old Streamlit UI now lives in deprecated/frontend/. Some older docs and tests still say frontend/; when they do, they are talking about the archived version. This guide describes the React app that actually runs at localhost:5173.

The one rule that explains the architecture

The browser is for showing things and collecting clicks. It never reads the database and never runs the AI pipeline. It asks a FastAPI backend for data, and the backend queues slow work as a background job. That separation is why a six-minute transcription does not freeze the page.

02 Run LecGap

Three steps to a working local app

You need two terminals: one for the Python backend, one for the React frontend. The frontend development server proxies API calls to the backend, so the browser sees everything as one origin.

Terminal 1 — start the backend

# From the repository root
# Generic setup: activate the project's Python environment first
# conda activate lecgap

python -m uvicorn backend.main:app --port 8000

On the machine this guide was verified on, the project dependencies are installed in Python 3.11, not the default Python 3.13. Use: 

py -3.11 -m uvicorn backend.main:app --port 8000

Backend health: http://localhost:8000/health. Interactive API docs: http://localhost:8000/docs.

Terminal 2 — start the frontend

cd frontend-react
npm install
npm run dev

Open http://localhost:5173. The Vite proxy forwards /courses, /lectures, /quizzes, /students, /jobs, /media, /usage, /health, and /llm to the backend on port 8000.

What you should see

  • A dark or light LecGap sidebar, a course picker, and three navigation groups.
  • The Overview page with a four-step progress strip.
  • The demo database already contains courses ml and prob.
  • The system status dot in the sidebar footer should settle on a live feed or polling.

Where the data lives

  • data/lecgap.db — the SQLite database.
  • data/raw/ — uploaded lecture media.
  • data/processed/clips/<lecture_id>/ — cut video clips.
  • data/lecturebank/ — the public benchmark used to fit the prerequisite classifier.
First-run gotcha

If python says No module named uvicorn or pytest, you are on the wrong interpreter. The repository's environment.yml describes the lecgap environment. On this machine, the working interpreter for the backend is py -3.11.

03 The big picture

Four layers, two kinds of traffic

Think of the app as a restaurant. The browser is the dining room. FastAPI is the waiter. The pipeline workers are the kitchen. SQLite and the media folders are the pantry. The dining room can ask for a dish and watch a progress screen, but it never walks into the kitchen and cooks.

Browser UI frontend-react/
React pages, shared components, React Query cache, Zustand UI state, SSE job feed. Shows data and sends user actions.
HTTP API backend/api/
FastAPI routes validate requests, read or write the database, queue jobs, and return JSON. It does not block on long pipeline work.
Workers and pipeline backend/api/jobs/ + backend/pipeline/
Background jobs run Whisper, the Lecture-Structure LLM pass, graph construction, ffmpeg clip cutting, and quiz generation.
Storage data/
SQLite stores rows for lectures, concepts, graph edges, clips, quiz questions, responses, and jobs. Files on disk store the actual video and clips.

Traffic type 1 — ordinary requests

Most screens use normal JSON requests: give me the lecture list, give me the graph, submit these quiz answers. These go through the single HTTP client in src/api/client.ts and are cached by React Query.

Traffic type 2 — live job updates

Slow operations return a job_id immediately. The backend runs the work in the background. The browser keeps one Server-Sent Events connection open to /jobs/stream and receives a fresh job snapshot whenever something changes.

Why this matters

In the old Streamlit app, the whole page re-ran on a timer to read a progress number. That restarted playing videos and made the page flicker. The React app fixes this by pushing job updates into a cache and only letting the components that display jobs subscribe to them.

The E2E test suite includes a real-browser test that plays a video while a real clip job runs, and asserts the video keeps decoding without restarting.

04 Frontend skeleton

From index.html to a routed page

The React app has a small, deliberate skeleton. Each layer owns one concern: providers, router, chrome, and the page itself. Understanding this tree makes every other file easier to place.

<!-- simplified, but every line exists in the real code --> index.html └─ #root └─ src/main.tsx └─ ErrorBoundary // last-resort crash screen └─ App (src/App.tsx) └─ AppProviders // React Query + Material UI theme └─ BrowserRouter └─ AppShell (components/layout/AppShell.tsx) ├─ Sidebar │ └─ CoursePicker ├─ AuthBanner ├─ Topbar ├─ ErrorBoundary // a broken page does not kill the shell │ └─ <Outlet> → lazy-loaded route view ├─ JobDrawer └─ JobCompletionHost

The providers

AppProviders installs exactly two things around the whole app:

  • QueryClientProvider — the React Query cache for server data.
  • AppTheme — the MUI theme plus the --lgc-* CSS variables for the current light or dark base.

Keeping these in one file means the real app and the test renderer cannot drift into two different theme stacks.

The shell

AppShell is the permanent frame:

  • Owns the single SSE connection.
  • Renders the sidebar, banner, topbar, routed page, job drawer, and completion snackbars.
  • Does not read job data itself, so a job tick cannot re-render the active page.
  • Wraps only the page outlet in an error boundary, so a broken page leaves the navigation usable.

A small leftover you may notice

components/layout/Navbar.tsx still exists, but nothing mounts it anymore. The current chrome is Sidebar + Topbar. The older README describes a top navigation bar because that was the earlier layout. If you are learning the current code, start with Sidebar and Topbar, not Navbar.

Why the routes are lazy-loaded

Every page is imported with React.lazy and rendered inside Suspense. That creates one JavaScript chunk per page. The browser downloads the Overview page first, and only downloads the heavy graph library (reactflow) when you open the Concept map. The production build output confirms this: DagView is its own large async chunk.

07 Four real journeys

Follow the data through the app

The fastest way to understand a system is to follow one action from click to result. These are the four journeys that matter most.

Journey 1 — Upload a lecture and get a transcript

  1. You choose a title and a file in UploadDialog.

    The dialog checks the course's existing lecture titles to warn about probable duplicates.

    components/student/UploadDialog.tsx
  2. Step 1: create the lecture row.

    The frontend sends a form request with the course and title. The backend creates a lecture in status uploaded and returns it immediately.

    POST /lectures → backend/api/routes/lectures.py
  3. Step 2: stream the media file.

    The file is sent with XMLHttpRequest so the browser can report real upload progress. The backend writes it to data/raw/ in chunks, then updates the lecture row with the file path.

    PUT /lectures/{id}/media → api/client.ts putStream()
  4. A transcription job is queued.

    The API creates a durable row in the jobs table, returns its id, and schedules a worker. The page does not wait for transcription.

    jobs.process_lecture → backend/api/jobs/transcribe.py
  5. Whisper produces timestamped segments.

    Depending on configuration, this is local Whisper or Groq's hosted Whisper. Long audio is downmixed and chunked. Each segment has a start time, an end time, and text.

    backend/pipeline/transcribe.py
  6. The lecture becomes ready.

    Segments are saved to transcript_segments, the lecture status flips to ready, and the job finishes. The SSE feed tells the UI, which refreshes the lecture list and snapshot.

    transcript_segments + jobs.status = ready

Journey 2 — Turn a transcript into a concept graph

  1. You click “Extract concepts”.

    This is only allowed for a ready lecture. The API checks status, queues an extraction job, and returns a job id.

    POST /lectures/{id}/concepts
  2. The Lecture-Structure pass reads the transcript in windows.

    It uses overlapping windows so a topic that crosses a boundary is seen in both. It asks the LLM for passages, concepts with teach spans, and prerequisite links that the professor actually said out loud.

    backend/pipeline/passages.py
  3. The worker saves three kinds of rows.

    passages describe teaching units. concepts point at their passage and carry start/end times. lecture_links store spoken prerequisites with verbatim evidence.

    backend/api/jobs/extract.py
  4. The course graph is rebuilt immediately.

    Concept names are deduplicated by embedding similarity. Spoken links become edges at confidence 0.9. A classifier fills only the pairs the transcript never grounded. Cycles are removed by dropping the weakest edge. The result is topologically sorted into learner order.

    backend/api/jobs/graph.py + backend/pipeline/build_graph.py
  5. The map and faculty views refresh.

    The graph is persisted in graph_nodes and graph_edges. React Query invalidates the course-scoped keys after the job finishes, so a visit to the map shows the new graph.

    GET /courses/{id}/graph

Journey 3 — Take a quiz and receive remediation

  1. You click “Start Quiz”.

    The frontend queues generation with a cap (15 by default). The backend returns 202 + job_id; the old synchronous endpoint is kept only for compatibility.

    POST /quizzes/jobs
  2. The quiz worker writes one MCQ per selected concept.

    Each question is grounded in the concept's teaching passage when available, with the old local transcript window as fallback. An LLM writes a question, a correct answer, three plausible distractors, an explanation, and per-distractor rationales. If the LLM fails, the pure evidence-based MCQ path still produces a gradable question.

    backend/pipeline/mcq_gen.py + backend/pipeline/quiz.py
  3. The browser reads the questions.

    When the job is ready, QuizView calls GET /quizzes. That endpoint only reads existing questions; it never regenerates them. The answer key stays on the server.

    GET /quizzes?course_id=…&student_id=…
  4. You answer and submit.

    The frontend sends only the selected option for each question. The backend grades server-side against the stored answer. It records a quiz_responses row and appends a new attempt.

    POST /quizzes/submit
  5. The remediation order is computed.

    Failed concepts are collected. The prerequisite graph is walked backwards to find everything upstream. The union is sorted by the graph's topological order, so foundations appear before the missed concept. Clips are attached when available.

    select_remediation_sequence() → backend/pipeline/quiz.py
  6. You get a study plan, not just a score.

    QuizPanel shows the score, per-question feedback, and the ordered remediation sequence. RemediationView can replay the same plan after a reload by calling the server endpoint.

    GET /students/{studentId}/remediation

Journey 4 — Watch a long job without refreshing the page

  1. An action creates a job before the worker starts.

    The row is inserted as queued. A client can attach to it immediately instead of waiting for the first progress update.

    jobs table + registry.create_job()
  2. The worker publishes progress.

    Every progress call updates the legacy in-memory store and the durable job row. The job carries a stage, detail, percentage, and heartbeat timestamp.

    backend/api/jobs/progress.py
  3. The browser keeps one SSE connection open.

    jobFeed.ts reads /jobs/stream with a streaming fetch. It parses data: lines, ignores keep-alives, reconnects with backoff, and falls back to reading GET /jobs once per failure cycle.

    src/lib/jobFeed.ts
  4. Snapshots land in one React Query key.

    useJobFeedConnection writes each snapshot to ['jobs', courseId]. Components that need job data read that key through useSyncExternalStore. The shell reads nothing, so a job tick cannot re-render the page.

    src/lib/useJobFeed.ts
  5. The drawer and badges update; finished work is announced once.

    The job drawer shows only live jobs. A completion host shows a snackbar once. Finished clips jobs also invalidate their per-lecture clip list; lecture jobs invalidate lecture detail.

    JobDrawer + JobCompletionHost + queryKeys
  6. Restart safety.

    If the server dies while a job is running, boot-time recovery marks stale running jobs as orphaned. The UI says the work was lost instead of showing a spinner that can never finish.

    recover_orphans() + heartbeat_at
08 Backend pipeline

Seven stages, and what each one actually does

The pipeline is split into small modules on purpose. Each one is mostly pure logic: it takes data in, returns data out, and lets the API/job layer decide how to persist it. That makes the stages testable without a browser, an LLM, or ffmpeg.

Transcription

backend/pipeline/transcribe.py

Converts lecture audio/video into timestamped text segments using Whisper. Local Whisper is the default; Groq's hosted Whisper is optional. Long files are downmixed to mono 16 kHz FLAC and chunked to fit upload limits.

In: media path → Out: [{start, end, text}]

Lecture-Structure pass

backend/pipeline/passages.py

One consolidated LLM read of the transcript in overlapping windows. It recovers teaching passages, concept teach spans, and spoken prerequisite links with verbatim evidence. The old chunk-atomic extractor remains only as a fallback.

In: transcript segments → Out: passages, concepts, links

Prerequisite classification

backend/pipeline/classify_prerequisites.py

For candidate concept pairs, predicts whether A must be understood before B. A temporal + embedding pre-filter avoids checking every possible pair. The adopted model is a frozen MiniLM encoder plus a logistic head, with F1 0.569 on the LectureBank benchmark.

In: concept names and times → Out: candidate edges + confidence

Graph construction

backend/pipeline/build_graph.py

Deduplicates concept names by embedding similarity (for example, “Gradient Descent” and “GD optimization”), adds transcript edges first, fills uncovered pairs with classifier edges, removes cycles by dropping the weakest edge, and computes a topological learner order.

In: concepts + spoken links + classifier pairs → Out: DAG + learner order

Clip segmentation

backend/pipeline/segment_clips.py

Runs ffmpeg once per concept over its teach span. Short clips are re-encoded for frame accuracy; very long clips use stream copy to save CPU. A failed clip does not abort the whole batch; the result row records the error.

In: lecture media + concept spans → Out: MP4 clips + clip rows

Quiz generation and grading

backend/pipeline/mcq_gen.py + backend/pipeline/quiz.py + backend/api/routes/quizzes.py

Writes one MCQ per concept from the teaching passage, with distractors and rationales. Falls back to an evidence-sentence question if the LLM fails. Grading is always server-side. Answered questions are preserved when a quiz is regenerated.

In: concepts + passages → Out: questions, answers, explanations, quiz responses

Remediation and refinement

backend/pipeline/quiz.py + experiments/refine.py

Remediation is live: failed concepts plus their transitive prerequisites, ordered by learner order. The graph-refinement experiment also exists, but it lives in experiments/refine.py and is not wired into a live API route. It validates the mechanism; it is not a production stage yet.

Live out: ordered remediation. Experiment: precision/recall/F1 recovery

Transcript-first, classifier second

This is the most important design choice in the graph. If the professor explicitly says something like “before we can understand backpropagation, recall the chain rule”, that sentence is strong evidence. The system stores it as a lecture_link with the exact quote and turns it into an edge at confidence 0.9. The classifier only fills pairs the transcript never grounded, such as cross-lecture relationships or silent jumps. That is why the graph view can show why an edge exists: a spoken quote or a classifier inference.

What the LLM is used for

  • Reading lecture structure: passages, concepts, and spoken prerequisites.
  • Writing quiz questions and explanations.
  • Optionally adding a second opinion to a classifier edge when LLM reasoning is enabled.

What the LLM is not trusted to do

  • Grade answers. Grading uses the stored answer key.
  • Silently delete edges. An LLM second opinion can adjust confidence, not hard-veto an edge.
  • Run without fallbacks. If the structure pass fails, the old extraction path is used.
Deep dive: why the graph is a DAG, and why that matters

A DAG is a directed graph with no cycles. “Directed” means each edge has a direction: Chain Rule → Backpropagation means the chain rule comes first. “No cycles” means you cannot follow arrows and arrive back where you started, which would make “what comes first?” unanswerable.

The graph builder removes cycles by finding the lowest-confidence edge in a cycle and dropping it, then repeating until no cycles remain. Transcript edges have high confidence, so they usually survive; a weak classifier guess is the one that gets dropped. The remaining graph can be topologically sorted, which is the learner order shown in the study sequence and used by remediation.

Deep dive: how clip cutting balances speed and accuracy

ffmpeg can cut in two ways. Stream copy (-c copy) is almost instant and lossless, but it can only start on a keyframe, so the first few seconds may jump backwards. Re-encoding (libx264) starts on the exact requested frame, but costs CPU time.

LecGap's default is a hybrid: clips up to 120 seconds are re-encoded for accuracy; longer spans use stream copy. Setting LECGAP_CLIP_STREAMCOPY=1 forces every clip to the fast path. Each concept is cut independently, and a failure is recorded per clip rather than aborting the whole lecture.

Why SQLite is enough here

This is a single-process local application, not a multi-server deployment. SQLite plus WAL gives durable rows, concurrent reads, and a busy timeout for writes. The database path is configurable with LECGAP_DATABASE_URL. Tests point it at a throwaway temp database so they never touch real data.

10 State and live updates

Three places state lives

React apps get confusing when one piece of data has several owners. LecGap splits state by what it is: server data, UI preferences, and a short-lived quiz draft.

React Query

Owns server data: courses, lectures, graph, stats, clips, usage, and the job-feed snapshot.

Fetches once, caches, and invalidates by key after writes.

Zustand

Owns UI state: selected course, student id, theme base, drawer open/closed, quiz draft, and completion notifications.

Changing UI state does not trigger an API call by itself.

Local component state

Owns things that only matter on one screen: dialog open, typed search, selected lecture, playing clip.

When the component unmounts, this state is gone, and that is correct.

One invalidation rule

Every course-affecting write calls invalidateCourse(queryClient, courseId). That helper clears the course list, all course-scoped keys for that course, and every per-lecture read. It exists because four hand-written invalidation lists had already drifted apart. One rule means a new write cannot forget one of the screens.

How the live job feed works

01 Worker writes stage, percent, heartbeat
02 SSE emits only when the snapshot changes
03 Feed parses data lines, skip keep-alives
04 Cache writes ['jobs', courseId]
05 Leaves read drawer, badge, jobs page

Feed modes

  • starting — the first connection is being opened.
  • stream — SSE is live and parsing frames.
  • poll — SSE failed, so the app falls back to reading GET /jobs.
  • unavailable — neither path is working; the UI says so.

Job states

  • queued — registered, not started.
  • running — a worker is publishing progress.
  • ready — finished successfully.
  • error — finished with a failure.
  • cancelled — the user settled the record.
  • orphaned — the server restarted and nothing is running it.
Why the shell does not read job state

AppShell renders the active page through <Outlet/>. If it subscribed to a value that changes every second, every page would re-render every second, and a playing video could restart. The shell only opens the connection. The drawer, badge, and Jobs page read the job cache as leaves. That separation is a core design rule, not a micro-optimisation.

Error handling you will meet

  • 401 — one AuthBanner at the top, with Retry.
  • Render crash — ErrorBoundary shows a panel and keeps the shell alive.
  • API failure — ErrorAlert shows the backend's detail message.
  • Stalled job — the drawer warns after a long silence.
  • Server restart — stale jobs become orphaned.

Where the API client lives

  • api/client.ts — the only file that calls fetch or XHR.
  • api/courses.ts, lectures.ts, quizzes.ts, jobs.ts, usage.ts — typed wrappers.
  • api/types.ts — shared TypeScript shapes.
  • The API key is added in one place, from VITE_LECGAP_API_KEY.
11 Theme and accessibility

One token system, two bases

The app supports a warm light theme and a dark espresso theme. The important part is that both come from the same small token table, so a colour cannot drift between the two.

Tokens

theme/tokens.ts defines the palette for light and dark: page, surface, border, text, status colours, graph colours, and node ink.

MUI theme

theme/muiTheme.ts maps those tokens into Material UI roles like primary, background.paper, and divider.

CSS variables

theme/variables.ts writes --lgc-* variables onto the document root so plain CSS and SVG can use the same values.

Rules the code follows

  • Components use semantic MUI slots or tint() / token() / gradient(), not raw hex values.
  • Graph node fills and label ink are calculated so text stays readable on both bases.
  • Status colours are contrast-checked against the surfaces they actually land on.
  • Rise honours prefers-reduced-motion and renders instantly when motion is reduced.
  • Icon-only controls carry an aria-label; the E2E tests address them by role and name.
  • Focus styles are visible, and the job feed status is announced, not only coloured.
The practical result

Switching the theme changes the MUI theme and the CSS variables together. A card background, a table header, a graph node, and a custom SVG band all re-derive from the same palette. That is why the light theme is not a separate stylesheet that slowly falls out of date.

13 Glossary

Plain-English definitions

Keep this nearby while reading the code. Most of the jargon in the repository is one of these ideas.

DAG
A directed graph with no cycles. Arrows show order, and you cannot loop back to the start.
Node
One concept in the graph. In LecGap, a node is usually a concept name such as “Slope” or “Backpropagation”.
Edge
A prerequisite link. A → B means A should be understood before B.
Topological order
A valid study order where every prerequisite appears before the concept that needs it.
Prerequisite
Something that must be learned first. “Chain rule” is a prerequisite of “backpropagation”.
Passage
A coherent stretch of a lecture where one topic is taught. It is the unit a student would re-watch.
Teach span
The exact start and end time where a concept is explained, not merely mentioned.
Transcript-first
Use prerequisite links the professor actually voiced as the primary graph evidence. The classifier fills only the gaps.
Classifier
A model that predicts whether one concept is a prerequisite of another. LecGap uses a frozen MiniLM encoder plus a logistic head.
Embedding
A list of numbers representing the meaning of text. Similar concept names have similar embeddings, which helps deduplication and candidate selection.
Deduplication
Merging names that mean the same thing, such as “Gradient Descent” and “GD optimization”, into one graph node.
Clip
A short video cut from the lecture around a concept's teach span.
Remediation
The ordered study plan produced after a quiz. It includes failed concepts and the prerequisites upstream of them.
SSE
Server-Sent Events. A one-way stream from the server to the browser, used here for live job progress.
Job
A durable record of background work: transcribe, extract, clips, graph, or quiz.
Heartbeat
A timestamp the worker refreshes while it is alive. If it goes stale, the job can be marked orphaned.
Orphaned
A job that was running when the server died. Nothing is executing it any more.
React Query
The library that owns server data in the frontend: fetching, caching, and invalidation.
Zustand
A small state library used for UI state such as selected course, theme, and the quiz draft.
Vite proxy
The development server forwards API paths to FastAPI on port 8000, so the browser can use same-origin requests.
MUI
Material UI, the component library used for buttons, cards, tables, dialogs, and the overall visual system.
Lazy loading
Downloading a page's JavaScript only when it is first opened. It keeps the initial load smaller.
